## 4. 缺陷清单（只记录，未修复）

### BUG-01【高·后端】参数微调「整体大小」无法应用：单位推导错误 PLAN_UNIT

- **现象**：对任意带"原网格编辑"方案的作品（例如欢迎作品、所有经 `model.adjust` 产生方案的作品），调用 `model.parameters.apply` 修改 `mesh_scale` 时，**同步**抛出 `DomainError("参数单位与尺寸或角度不一致。", "PLAN_UNIT")`，任务根本不会创建。UI 上该功能就是造物桌的「参数微调」面板（唯一主参数即"整体大小"滑杆）——**该功能 100% 不可用**。
- **复现**（已固化为 `TC-I-011`，标记 `xfail(strict=True)`）：
  ```bash
  curl -s -X POST http://127.0.0.1:5173/api/rpc -H 'Content-Type: application/json' \
    -d '{"method":"model.parameters.apply","params":{"schema_version":1,"id":"<作品id>","base_revision_id":"<版本id>","parameters":{"mesh_scale":1.5}}}'
  # → {"error":{"message":"参数单位与尺寸或角度不一致。"}}
  ```
- **根因定位**：`backend/yaha/modeling/compiler.py:65`（`resolve`）与 `compiler.py:44-56`（`unit`）。`unit()` 对 `multiply(数值, ratio)` 表达式（如 `model.height = 80 × mesh_scale`，由 `mesh_editing.py` 的 `editable_spec` 生成）返回 `"ratio"`，而约束期望单位为 `"mm"`，于是 `resolve` 判定单位不一致直接报错。乘法单位推导应为「`None × ratio → None`（无量纲×未知=未知）」，当前实现 `result = b if a in (None, "ratio") else a` 在 `a=None` 时错误地取了 `b`。
- **影响**：产品 UI 明确暴露的参数微调能力对存量作品全部失效；`describe` 能列出参数、`apply` 必然失败，属于功能级回归。
- **证据**：`gui-test-screenshots/t11_param_panel.png`（面板与滑杆正常）、`t12/t13/t14_param_apply*.png`（应用无任何效果）。

### BUG-02【高·前端】参数微调应用失败时无任何用户反馈（静默吞错）

- **现象**：在参数微调面板把"整体大小"改为 1.5 并点击「立即应用参数」（含"松手应用"路径）后：无报错、无 toast、无任务创建（`job.list` 无新记录），面板停留在"已调整 1 项 · 应用后保存新版本"状态，按钮可反复点击。后端抛出的 BUG-01 错误被前端完全吞掉。
- **复现**：造物桌 → 「参数微调」→ 整体大小改为 1.5 → 点「立即应用参数」→ 观察无任何反应（截图 `t12_param_apply_bug01.png`、`t13_apply_transient.png`、`t14_apply_after.png`）。
- **影响**：孩子/家长视角是"按钮坏了"，且没有任何解释；叠加 BUG-01 使该功能从前后端两层同时失效。
- **备注**：修复 BUG-01 后此问题仍需独立修复——前端应对 `model.parameters.apply` 的同步 DomainError 呈现明确提示。

### BUG-03【中·前端】版本切换成功后，版本号标签不更新（显示旧版本号）

- **现象**：在「版本时光机」把"我的新作品"从 v10 切换到 v09：toast 提示"已切换作品版本"、3D 模型几何确实变为 v09（底部尺寸由 47.6 变为 56.3 mm 宽），后端 `project.get` 确认 `revision_id` 已指向 v09；**但顶部版本胶囊、3D 视口右上角、聊天流系统消息全部仍显示"v10 / 版本 10版 / 版本 #10"**。用户会以为自己在 v10，实际在 v09。
- **复现**：造物桌（我的新作品）→ 右下「版本 10版 ▾」→ 选 09「Blender 建模」→「切换到这一版」→ 观察版本标签仍为 10（截图 `t16_switch_v09.png`、`t17_bug03_version_stale.png`）。
- **API 证据**（切换后只读查询）：
  ```
  当前 revision: c9ec612b…（= v09 "Blender 建模"）
  history: b9c81673(v10 AI 细节调整) / c9ec612b(v09 Blender 建模) / …
  ```
- **影响**：状态误导，属数据一致性/信任问题；后续在"以为是 v10"的版本上继续对话或微调会产生认知偏差。
- **备注**：测试结束后已将作品切回 v10 并经 API 确认。

### BUG-04【中·前端】首页想法输入框无法清空（旧草稿立即回填）

- **现象**：在首页大输入框执行清空（`fill("")` 等价于用户全选删除）后，输入框的值**立即**恢复为之前的草稿内容"做一个乌萨奇的摆件"（清空后 200ms 与 1.5s 两次读取值相同）。用户无法清空输入重新开始；清空后点「立即造物」弹出的命名框也会带上旧草稿文本（截图 `t19_empty_input.png`）。
- **推测根因**：输入草稿的持久化/恢复状态机与受控输入值不同步——`onChange` 收到空串后未写入状态（或存在 `value || lastDraft` 兜底），导致空值被旧草稿覆盖。
- **影响**：中等。不阻塞造物（旧内容仍可编辑），但"重新开始一个想法"的路径被破坏，且空输入边界防护因此从未真正生效。

### 5. 其他观察与次要问题（不构成阻断）

1. **ARIA 树控件冗余**：首页"最近作品"下拉中的每个条目在可访问性树中出现两份（Playwright 计数为 2），视觉上只有一份（`t10_recent_dropdown.png`）。疑似响应式双渲染，对屏幕阅读器用户会造成重复朗读。
2. **fullPage 截图伪影（非产品缺陷）**：对本应用做整页截图会出现 2×2 内容重复（`t03_print_station.png`），普通视口截图正常（`t03b`）。判断为该页面使用视口锁定布局与截图器整页拼接不兼容，记录以免误判。
3. **NaN 尺寸钳制怪异行为**：`DesignSpec` 的尺寸自愈对 `NaN` 输入产出**上界值**（如 `height_mm=NaN → 500`）而非默认值，见 `TC-C-009`。建议钳制函数对非有限数回退默认。
4. **上传预检阈值与文案**：`assets.upload` 以"base64 长度 > 18MB"作预检但报错文案写"超过 12 MB"；实际有效限制（解码后 12MB）与文案一致，预检只是提前退出，属冗余代码而非缺陷。

### 5.3 既有引擎套件的 1 个失败（既有测试债，非本次引入）

- `tests/engine/test_modeling_quality.py::test_planner_repair_receives_multiple_coordinate_errors`
- **原因**：测试夹具 `keychain()` 生成的方案 `schema_version` 仍为旧值，而 `planner.py:110` 现要求"新方案须使用 schema_version=8"，第一轮校验即抛 `PLAN_COORDINATES`，走不到测试期望的"坐标错误合并重试"分支。**属测试夹具未跟随契约升级**。其余 109 个用例全部通过（对比 2026-10-17 快照的 10 个失败，工作区改动已修复大部分旧债）。

## 7. 覆盖与未覆盖范围

**已覆盖**：数据契约与自愈、作品/版本/素材/会话/素材目录存储、家长与打印密码、云端额度门禁、任务生命周期、打印体检、多格式导出导入、真实 Blender 模板建模与修复、真实 Bambu Studio 切片、主要 GUI 流程。

**未覆盖/受限**：
- 云端 AI 生成质量（照片参考建模、AI 对话改型）——需要真实云端调用且有额度消耗，仅验证了门禁与失败路径；GUI 测试中一次真实云端推演已即时停止。
- 拓竹实机云打印（登录、选机、实机发送）——涉及真实账号与硬件，按项目约定"测试不得自动触发真实打印"跳过；`bambu_print` 未切片拒绝路径已由 TC-R-017 覆盖。

## 9. 2026-10-22 逐项源码复核与修复

本次依据当前源码、已有测试断言、截图及只读数据库记录核对；没有执行复现、回归或端到端用例。以上“均未修复”仅描述原报告时点。

### BUG-01：确认，已修复单位推导

1. **产生原因**：`editable_spec` 以 `原始高度常量 × mesh_scale(ratio)` 定义毫米高度；编译器将未标注单位的数值常量与比例相乘时错误地固定为 ratio。
2. **现象**：`apply_parameters → compile_plan → resolve` 在创建任务前拒绝 model.height。既有 TC-I-011 已记录此失败；本轮未重跑。
3. **根因**：乘法分支把 `None` 和 `ratio` 当成同类，`None × ratio` 取右侧 ratio；反向 `ratio × None` 却为 None，违反乘法对称性。
4. **本质**：常量单位由使用位置确定，不能由无量纲比例赋予固定单位。
5. **修复**：仅修改乘法返回规则：ratio 保留另一操作数的单位，其他合法组合保留已知单位。`None × ratio` 与反向均为 None，交给 resolve 的尺寸上下文处理；`mm × ratio` 仍为 mm；`mm × mm` 仍拒绝。移除 TC-I-011 的 strict xfail，保留真实网格高度及 ai_used=false 断言。
6. **验证边界**：Python AST 与差异格式检查通过；真实 Blender 参数重算尚未执行。影响确定为原网格整体缩放，报告“所有参数微调 100% 不可用”的泛化不成立。

### BUG-02：确认，已补齐弹窗内错误传递

1. **产生原因**：参数面板调用共享 `act` 包装器；包装器捕获异常后只设置全局 notice，返回 undefined。
2. **现象**：后端同步失败，没有任务可供面板观察；参数面板仍显示“已调整”。
3. **根因**：`useParameterDraft.apply` 未接收到失败原因，面板 error 保持空。全局 toast 位于原生 modal dialog 外，不能作为弹窗内可靠反馈。
4. **本质**：请求失败的状态没有传回发起请求的交互组件，不是后端完全未返回错误。
5. **修复**：共享 action 增加可选错误回调，参数提交将原错误传给面板已有 error/aria-live 提示区；保留全局提示、任务互斥及 busy 的 finally 清理。
6. **验证边界**：回调与展示调用链已静态核对。按钮、松手应用共用该提交路径；没有运行浏览器操作或注入失败测试。未改变布局和主题样式。

### BUG-03：确认，已区分当前序号与版本总数

1. **产生原因**：Project 只提供 revision_id 和 revision_count，多个界面直接以总数显示当前版本。
2. **现象**：切换 v10 → v09 不减少历史总数，标签仍取 10。
3. **根因**：`select_revision` 正确更新 revision_id，消费者读取的却是 revision_count。只读数据库确认作品 `0e9c855d-e8c0-4af6-b99d-5becbf913883` 有 10 版，`c9ec612b-a822-499b-a821-f132f5a1b0ea` 排第 9；当前已在 v10，本轮未切换。
4. **本质**：当前版本身份与集合数量混用。
5. **修复**：Projects.get 按当前 revision_id 和历史列表相同顺序派生 revision_number；创建版本与切换返回重新读取的 Project。顶部胶囊、视口、聊天里程碑、参数弹窗统一读取新字段；历史数量统计仍用 revision_count。旧数据读取时计算，无需修改历史版本或迁移数据库；旧响应缺字段时显示未知标记，不伪装为最新版本。
6. **验证边界**：数据库只读取证和 Python/TS 语法检查完成；版本切换、新建候选、删除及恢复后的运行回归仍待执行。序号沿用现有历史列表规则，删除历史后会重新排列，并非新增永久版本编号机制。
